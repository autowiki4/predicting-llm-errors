# Predicting When LLMs Get It Wrong

*A small, practical study of whether simple response features can flag unreliable AI answers.*

An LLM answer can sound polished and confident and still be wrong. This project does
**not** try to fix hallucinations. It tests one focused, measurable idea:

> **Research question.** Can simple features from an LLM response help predict whether the answer is correct or unreliable?
>
> **Working hypothesis.** A combination of response length, consistency, confidence cues and self-check behaviour will predict errors better than chance.

The repository is a complete, reproducible pipeline that answers that question with evidence:
it asks an LLM questions with known answers, labels each answer right or wrong, turns every
response into a handful of numbers, trains small classifiers to spot the wrong ones, and
reports whether they beat simple baselines, with confidence intervals and significance tests.

```
 Questions  ──►  Responses  ──►  Features  ──►  Classifier  ──►  Evaluate
 GSM8K with      LLM answers,    length, hedging,  logistic reg.,   accuracy, F1, precision/
 known answers   extra samples,  consistency,      random forest,   recall for wrong answers,
                 self-check      self-check        gradient boost.  vs. baselines, CIs, p-values
```

## Quick start (2 minutes, no API key)

```bash
git clone <this repo> && cd predicting-llm-errors
python -m venv .venv && source .venv/bin/activate     # Windows: .venv\Scripts\activate
pip install -e ".[all]"

llmrel run --config configs/demo.yaml                 # whole pipeline, ~30 seconds
pytest                                                # 73 tests, ~1-2 minutes
```

Then open `runs/demo/report.md` (the written results) or the notebook:

```bash
jupyter notebook notebooks/walkthrough.ipynb
```

> **About the demo.** `configs/demo.yaml` uses a built-in **simulated LLM** so that everything
> runs offline and for free. Its errors are generated by a hand-made model, so its results prove
> only that the code works, **not** anything about real LLMs. Every report produced from simulated
> data carries a warning banner. For real results, see the next section.

## Running the real experiment

Pick one model to study. The pipeline is identical for all of them; only the config changes.

### Option A: Claude (Anthropic API)

```bash
export ANTHROPIC_API_KEY=sk-ant-...                       # never put keys in config files
llmrel estimate --config configs/claude.yaml              # how many API calls this will make
llmrel run --config configs/claude.yaml --set data.n_questions=20   # cheap trial run first
llmrel run --config configs/claude.yaml                   # the full 1,000-question run
```

### Option B: a free local model (Ollama)

```bash
# install Ollama from https://ollama.com, then:
ollama pull llama3.2:3b
llmrel run --config configs/ollama.yaml
```

Any server that speaks the OpenAI chat API works (LM Studio, vLLM, hosted OpenAI-compatible
APIs). Change `base_url` and `model` in the config.

### Things worth knowing before a real run

* **Calls per question.** `1 main + n_samples extra + 1 self-check` = 7 with the defaults, so
  1,000 questions is 7,000 calls. `llmrel estimate` prints the exact number. Setting
  `collection.n_samples: 0` and `collection.self_check: false` gives a cheap run that uses
  only the free features.
* **You need enough wrong answers.** The classifiers learn from mistakes. If the model gets
  98% right, there are only ~20 errors to learn from and the results will be noisy (the pipeline
  stops with a clear message if there are too few). Aim for an error rate between roughly 10% and
  40%: use a smaller model, lower `effort` for Claude, or more questions
  (`llmrel download-data --split train` adds 7,473 more GSM8K questions; point `data.path` at
  `data/raw/gsm8k_train.jsonl`).
* **Collection is resumable.** Responses are appended to `runs/<run_name>/responses.jsonl` as soon
  as each question finishes. If a run is interrupted, or some calls fail, run the same command
  again and only the missing questions are requested.
* **Raw responses are the valuable part.** Once collected, you can change features or models and
  re-run `llmrel features` and `llmrel evaluate` for free.
* **Stretch goal: comparing two LLMs.** Give each model its own config with a different `run_name`,
  run both, and compare the two reports.

## What you get from a run

Everything is written to `runs/<run_name>/`:

| File | What it is |
|---|---|
| `responses.jsonl` | Raw LLM output: main answer, extra samples, self-check, token usage |
| `run_config.json` | The exact config and prompts used (for reproducibility) |
| `features.csv` | One row per question: every feature plus the `is_wrong` label |
| `results/test_metrics.csv` | Test-set metrics for every model and baseline, with 95% CIs |
| `results/cv_metrics.csv` | 5-fold cross-validation scores on the training set |
| `results/ablation.csv` | Performance with each feature group alone / removed |
| `results/feature_importance.csv` | Permutation importance of each feature |
| `results/summary.json` | Dataset summary and all hypothesis-test results |
| `figures/*.png` | Six figures ready for slides (see below) |
| `report.md` | Plain-language write-up that answers the research question |

Figures produced: `model_comparison.png` (baseline vs. simple vs. combined, the proposal's
headline chart), `roc_pr_curves.png`, `feature_importance.png`, `ablation.png`,
`feature_distributions.png` and `confusion_matrix.png`.

A complete example run on simulated data is included in [`runs/demo/`](runs/demo/report.md).

## How it works

Each stage is one module in `src/llm_reliability/`, and each module starts with a docstring
explaining what it does and why. Full details, including every feature definition and the
statistical tests, are in [docs/METHODOLOGY.md](docs/METHODOLOGY.md).

### 1. Questions: `data.py`
[GSM8K](https://github.com/openai/grade-school-math) grade-school math word problems. Each answer
is a single number, so correctness can be checked automatically. A reproducible random sample of
1,000 of the 1,319 test questions is used by default. The dataset is bundled in `data/raw/`
(MIT licence).

### 2. Responses and labels: `collect.py`, `grading.py`, `prompts.py`
The model is asked to reason step by step and finish with `Answer: <number>`. For each question:
one main answer, `n_samples` extra answers to the same prompt, and one self-check in which the
model grades its own answer (`Verdict: CORRECT/INCORRECT`, `Confidence: 0-100`).
The final number is extracted and compared with the reference, giving the label
**`is_wrong`** (1 = wrong). "Wrong" is the positive class because the goal is to flag errors.

### 3. Features: `features.py`

| Group | Cost | Features | Intuition |
|---|---|---|---|
| Length | free | characters, words, sentences, lines, numbers, output tokens | struggling answers ramble |
| Confidence language | free | hedges ("I think", "probably"), certainty words ("clearly"), self-corrections ("wait", "actually") | wording reveals uncertainty |
| Answer format | free | used the requested format? answer missing? whole number? | sloppy format suggests sloppy reasoning |
| Consistency | extra calls | agreement with re-samples, number of distinct answers, answer entropy | a model that knows the answer gives it every time |
| Self-check | extra call | says its own answer is incorrect, stated confidence | can the model catch its own mistakes? |

**Simple features** = the three free groups. **Combined features** = all five.

### 4. Classifiers and baselines: `models.py`
Logistic regression, random forest and gradient boosting, all with class re-weighting (wrong
answers are the minority). They must beat three kinds of baseline: *majority class*
(always predict "correct"), *random guessing*, and *single-feature rules* (for example
"flag if fewer than 60% of re-samples agree") whose thresholds are tuned on the training data.

### 5. Evaluation: `evaluate.py`, `plots.py`, `report.py`
* A **held-out test set** (25%) is used only once, at the end.
* The best model per feature set is chosen by **cross-validation on the training set**, never by test score.
* Metrics: **ROC-AUC** (primary: threshold-free, robust to imbalance), accuracy, balanced
  accuracy, **precision / recall / F1 for wrong answers**, PR-AUC.
* **95% bootstrap confidence intervals** on every test metric.
* **Hypothesis tests:** a label-permutation test for "better than chance", and paired bootstrap
  tests for "combined beats simple" and "combined beats the best single rule".
* **Which features matter:** feature-group ablations and permutation importance.

## Command reference

```text
llmrel run       --config FILE   collect -> features -> evaluate
llmrel collect   --config FILE   query the LLM only (resumable)
llmrel features  --config FILE   responses.jsonl -> features.csv
llmrel evaluate  --config FILE   features.csv -> results/, figures/, report.md
llmrel estimate  --config FILE   count the LLM calls a run needs (makes none)
llmrel download-data --split {train,test}

--set KEY=VALUE   override any config value, e.g. --set data.n_questions=50
-v                debug logging
```

`python -m llm_reliability ...` works the same as `llmrel ...`. `make help` lists shortcuts.

## Testing

```bash
pytest                # everything (~1-2 min)
pytest -m "not slow"  # fast tests only (~30 s)
ruff check src tests
```

The tests cover answer extraction and grading edge cases, every feature, the simulator, resumable
and fault-tolerant collection, the metrics (checked against scikit-learn), the statistical tests,
all three classifiers, the full pipeline through Python and the CLI, the notebook, and both API
clients. The Claude and OpenAI-compatible clients are exercised through the real SDKs against
small local fake servers, so the exact request each one sends is checked without needing a key.
CI runs the suite on Python 3.10 to 3.13 (`.github/workflows/ci.yml`).

## Limitations

* One task type (grade-school math). Signals that work here may not transfer to open-ended questions.
* Exact numeric matching: a correct answer in an odd format counts as wrong (the
  `answer_explicit` feature tracks how often this could matter).
* Consistency and self-check features cost extra calls, so they are not "free" signals.
* The simulated LLM exists only for demos and tests. Never report its numbers as findings.
